Build any web or mobile app with your own AI agent team

A repeatable recipe: pick an idea and an API, have Claude research it, design a team of expert agents, give each one skills, a knowledge folder and the right brain, talk to them about the architecture, then ask one orchestrator to build the app together. The finished app even has an Agents page where you keep talking to your team, and they change the live app for you.

1

How the technique works

You are about to build a team of AI experts that designs, builds, tests and keeps improving your app. Here are the five pieces, plus the twist: the agents live inside your finished app too.

This technique works for any web or mobile app. Instead of asking one AI to do everything, you build a small company of AI experts inside your repository, give each one real knowledge and the right brain, and run them through one lead. Five pieces make it work.

The people

Agents

What they are: one Markdown file each in .claude/agents/. The file says who the expert is, what tools it may use, and its rules.

Why: a security expert and a designer think differently. Separate agents keep each one focused, and they can run in parallel.

---
name: security-engineer
description: Reviews anything touching secrets...
model: opus
skills: [secure-by-design, supabase-auth]
---
The playbooks

Skills

What they are: folders in .claude/skills/, each with a SKILL.md of team conventions (how we deploy, how we commit, how we test).

Why: skills are shared. Write "how we call Open-Meteo" once and every agent that needs it gets the same rules.

The expertise

Knowledge folders

What they are: knowledge/<agent>/docs (notes from the official documentation, with source links) and examples/ (small code that was actually run).

Why: an agent without knowledge answers from memory, which can be old or wrong. With it, the agent works from the docs you chose.

The brains

Models

What they are: the model: line in each agent file: opus for hard reasoning, sonnet for strong everyday work, haiku for small fast jobs. Each agent also gets a name and personality.

Why: you pay for the big brain only where a mistake is expensive.

The lead

Orchestrator

What it is: the one agent you talk to. It plans the work in waves, launches every expert whose inputs are ready at the same time, passes results between them and has them review each other.

Why: you ask one question and get a team's answer.

The twist

Agents inside your live app

What it is: an Agents page in the deployed app. You log in as the super admin, chat with any agent, and when it proposes a change you click Approve: it commits to GitHub and Netlify redeploys.

Why: your team keeps working on the app after it ships, from your phone.

The worked example: Beach Day, an installable phone app (PWA) that scores today's South Florida beach weather using the free Open-Meteo API, with Supabase login (email or Google). Swap in your own idea and API; every step stays the same.

2

Pick an idea and a free API

Every app needs data. Start from an API that is free, needs no key, and is beginner friendly, so nothing blocks you on day one.

  1. Open the Vibe Coding API Directory. It lists thousands of free APIs, MCP connectors, skills and step-by-step setup guides.
  1. Turn on the No key needed and Beginner friendly filters, search for your topic, and open a card. How to get access tells you exactly what you need.
  1. Look up the Claude API card too. Your deployed app uses it so the agents can answer you from the Agents page.

Good to know: Write your idea in one sentence before you start. Mine: "Pick a South Florida beach and see whether today and the next few days are good beach days."

3

Create a GitHub repository

The repository holds everything: research, agents, skills, knowledge and the app. Netlify deploys straight from it, and the Agents page commits to it.

  1. On GitHub click Repositories, then New.
  1. Name it (I used BeachDay), add a description, switch Add README on, and click Create repository.
4

Open it in Claude Code

Claude Code on the web reads and writes your repository directly, and runs your agents.

Before you start: connect GitHub in Claude (Customize → Connectors). For the login step you will also connect Supabase there.

  1. Go to claude.ai/code, click New, pick your repository under the message box.
  2. Choose Opus 5.5, Medium effort.
5

Research from the official docs

The research decides the architecture. Make Claude read the real documentation for your API, your platform (PWA, Netlify) and the Claude and GitHub APIs before anyone writes code.

Paste this into Claude Code (change the idea and API to yours)
I want to build a mobile-friendly web app that people can install on their phone (a Progressive Web App, or PWA) and that is deployed on Netlify. My idea is Beach Day: pick a South Florida beach and see whether today and the next few days are good beach days. It uses the free Open-Meteo API (weather, UV, wind and rain, plus the Marine API for waves and sea temperature). No API key is needed; I found it on https://mcp-api.netlify.app/. Read the official docs first: the Open-Meteo forecast and marine APIs (https://open-meteo.com/en/docs and https://open-meteo.com/en/docs/marine-weather-api), MDN's Progressive Web Apps guides (manifest, service worker, installability), Netlify's docs (static deploys, Functions, environment variables, Netlify Blobs, and function time limits including streaming and background functions), the Claude API docs (Messages API, models, tool use, streaming) and the GitHub REST API docs for updating repository contents with a fine-grained personal access token. Research: (1) the use case and how to score a "beach day" from the API fields, with sources; (2) what makes a PWA installable on iPhone and Android, and when you would need a native wrapper such as Capacitor instead; (3) an architecture for a static Netlify site plus Netlify Functions; (4) an Agent Console inside the deployed app: a page that lists every agent in .claude/agents with its name, model and personality, lets the user chat with any agent (the Claude API is called only from a Netlify Function, with the key in an environment variable), and lets an agent propose code changes that are committed to GitHub only after the user clicks Approve, which triggers a Netlify redeploy. Research the security for that (password gate, a fine-grained token limited to this one repository, an allow-list of paths agents may change, no secrets in the browser, rate limits) and how to handle long agent jobs within Netlify's time limits; (5) testing and accessibility. Put the results in a docs folder (one markdown file per topic plus a README index) and push it to the main branch on GitHub. This is context for a team of expert agents we will build next.

Check it worked: Open the docs folder on GitHub and confirm the files are on main.

Good to know: Queue the next prompt while Claude works: type it and press ⌘ + Return (Mac) or Ctrl + Enter. Send one at a time, or they can merge into a single turn.

8

Give every agent a knowledge folder

This is what turns a generalist into an expert. Each agent gets notes from the official docs (with sources) and worked examples that were actually run, and must read them before it answers.

Do not skip this step. Without knowledge, an agent answers from memory, which can be out of date.

Paste this into Claude Code
Now give every agent its own knowledge. Create knowledge/<agent-name>/ for every agent in .claude/agents/, with two subfolders: docs/ (real reference notes taken from the official documentation, each with its source link) and examples/ (two or three small, correct worked examples that show what good looks like). The API integration expert gets notes and examples from open-meteo.com (forecast and marine endpoints, the fields we use, units, time zones, caching); the mobile/PWA expert from MDN and web.dev (manifest, service worker, install prompts on iOS and Android); the agent-console engineer from the Claude API docs (Messages API, models, streaming, tool use) and the GitHub REST API (get and update file contents, commits); the security expert from OWASP and GitHub's fine-grained token docs; the Netlify engineer from Netlify's docs (functions, environment variables, Blobs, headers, time limits); the UI and UX designers from Apple's Human Interface Guidelines; the QA engineer from the Playwright docs; and so on for every agent. Run any code example you can to prove it works. Then add a "Before you answer" section to every agent file that says: read every file in your knowledge folder first and prefer it over memory. Push everything to main.

Good to know: Add your own files any time: drop a PDF or notes into knowledge/<agent>/ and push. That agent reads it next time.

Talk to your agents before you build

Interview your experts. Ask the architect, the API expert, the security expert and the mobile expert hard questions now: they catch problems while they are still cheap to fix.

Start a new Claude Code session first. Agents created during a session may not load until the next one. Click New, pick the same repository, then type @agent- and the agent name.

1. The architect: how does it all fit?

Paste this into Claude Code
@agent-software-architect Read docs/ and docs/expert-roster.md. Draw the Beach Day architecture as a simple text diagram (browser, service worker, Netlify Functions, Open-Meteo, Claude API, GitHub, Netlify redeploy), list the folders and files you would create, and name the three biggest risks with how you would reduce each one.

2. The API expert: show me real data

Paste this into Claude Code
@agent-open-meteo-integrator Call the Open-Meteo forecast and marine APIs for Miami Beach right now. Show me the exact URLs, the fields we will use for the beach score, a short sample of the real response, and how you would turn those fields into a 0 to 100 beach score.

3. The security expert: who can change my app?

Paste this into Claude Code
@agent-security-engineer The deployed app will let agents change our code from a chat page. How do we stop strangers from doing that or spending our API credits? Give me your rules, in order of importance, and what each environment variable is for.

4. The mobile expert: will it install on my phone?

Paste this into Claude Code
@agent-pwa-mobile-engineer What exactly makes Beach Day installable on an iPhone and on an Android phone? Give me the checklist, and the one mistake people make most often.

Good to know: Each expert ends with decisions for you. Answer them in one message to the orchestrator, and it routes each answer to the right expert.

11

Add login: email, Google and one super admin

Your agents can change your app and spend your API credits, so only you may use them. Supabase gives you sign-up, log-in and Google sign-in, and a role on your profile marks you as the one super admin.

Follow the two guides in the directory: Email and password login with Supabase and Sign in with Google using Supabase.

Paste this into Claude Code (it answers the experts' decisions too, if you add them at the top)
@agent-orchestrator Add login with Supabase Auth. Users can register and log in with email and password (sign up, log in, log out, forgot password) and with Continue with Google (signInWithOAuth, provider google). Add a profiles table linked to auth.users with a role column (default user, row level security so people read only their own row and can never change their role). Only the super_admin role can open the Agents page, chat with agents, or Approve changes; every Netlify Function checks the Supabase access token and the role on every request. Use only the Supabase project URL and publishable key, never the secret key. Use the same process as before: have agent-builder add a supabase-auth-engineer agent with its own skills, a knowledge folder (notes from the official Supabase Auth, supabase-js, Google sign-in and row level security pages with sources, plus tested examples) and a brain in docs/agent-brains.md. Update the roster, the decision records, the security docs and the build plan. Run independent experts in parallel and push to main. Don't build the app yet.

Set up Supabase and Google (about 15 minutes, once)

  1. In the Supabase dashboard click New project, name it, click Generate a password, tick Enable RLS on new tables automatically, and click Create new project.
  2. Open SQL Editor, paste the file supabase/migrations/…_profiles.sql your team wrote, and click Run. It creates the profiles table with a role column that users can never change themselves.
  1. Authentication → URL Configuration: set Site URL to your Netlify address and add two redirect URLs: https://your-site.netlify.app/** and http://localhost:8888/**.
  2. Authentication → Sign In / Providers → Google: copy the Callback URL.
  1. In Google Cloud create a project, open Google Auth Platform → Get started, fill in the app name and support email, choose External, agree, and click Create.
  2. Clients → Create client → Web application. JavaScript origins: your Netlify address and http://localhost:8888. Redirect URI: the Supabase Callback URL. Click Create.
  1. Back in Supabase's Google panel, turn on Enable Sign in with Google, paste the Client ID and the Client secret, and click Save.
  2. In Google Cloud, Audience → Test users: add your own Gmail. While the app is in Testing, only listed users can use Continue with Google.

You paste the secrets, not Claude. The Google client secret goes only into Supabase. Never put it in your code, a prompt or GitHub.

Good to know: Students and visitors do not need Google at all: they can register with email, and the beach pages need no account.

13

Deploy on Netlify and add your keys

Netlify builds from GitHub. The secret keys live only in Netlify, never in your code or a chat.

  1. In the code, replace the placeholder Supabase host in public/_headers with your real project URL (or ask the orchestrator to). The build fails on purpose until you do: a safety check.
  2. In Netlify: Import from Git → GitHub, pick your repo, name the project, and add two public variables: SUPABASE_URL and SUPABASE_PUBLISHABLE_KEY (from Supabase → Settings → API Keys; it starts with sb_publishable_). Click Deploy.
  1. Project configuration → Environment variables: add ANTHROPIC_API_KEY and GITHUB_TOKEN, tick Contains secret values for each.
  • ANTHROPIC_API_KEY: console.anthropic.com → a separate workspace with a low spend limit → API key.
  • GITHUB_TOKEN: github.com/settings/personal-access-tokens/new → fine-grained, only your repo, Contents: Read and write, 90 days.
  1. Turn off Deploy Previews, then Deploys → Trigger deploy so the functions pick up the keys.

Never paste a key into a chat, a prompt or your code. Keys live only in Netlify. If one leaks, delete it and make a new one.

Change your live app by talking to your agents

Log in as the super admin, open the Agents page, ask an agent for a change, review the diff and click Approve. GitHub gets the commit and Netlify redeploys.

Type this on the Agents page
Change the beach score so wind over 20 mph lowers the score more, and add a line under the score that says when the best two-hour window is today.

Make yourself the super admin (once)

  1. On your live app, open Agents and sign in. You will see "no access": every new account starts as a plain user.
  2. In Supabase → SQL Editor, run supabase/manual/promote-super-admin.sql: step 1 shows your account, step 2 promotes it.
  3. Reload the Agents page: you now see every agent with its name, model and personality.
