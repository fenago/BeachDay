Step-by-step guide

How Beach Day was built and put on the web, in order.

Steps 5 onward need your own Supabase, Google, GitHub, Anthropic and Netlify accounts. At the time of writing no live site is linked, so this guide does not point to one.

  1. Write the design first

    Decisions live in docs/: use case and scoring, the installable app, Netlify, Agents, the Claude API and testing. Short decision records sit in docs/adr/. Start with docs/README.md.

  2. Set up the agent team

    Twelve specialist agents live in .claude/agents/, with shared skills in .claude/skills/. Each agent has its own knowledge folder in knowledge/. One agent, the orchestrator, plans the work and passes it between the others.

  3. Build in waves

    Wave 0 lays the npm and test foundation. Wave 1 builds the pieces that do not depend on each other, in parallel. Each wave ends with read-only reviews by the experts whose area the change touches, and owners fix only the required items. Wave 2 builds screens and handlers on top. Wave 3 is the full test run, the local run and the final security review. Wave 4 fixes what they found.

  4. Prove it locally

    Install, run the unit tests, then the phone-sized browser tests:

    npm ci
npx vitest run
npx playwright test --trace off

    Serve the whole site on your computer with fake sign-in, Claude and GitHub services, so nothing real is called:

    node tests/harness/server.mjs

    Then open http://127.0.0.1:4173. To prove the Netlify build, run npx netlify build --offline.

  5. Create the Supabase project

    Do this once you have a Supabase account. Create a project on the Free plan and note the project URL and the publishable key. Never copy the secret key or the service_role key anywhere. Try supabase/migrations/20261123000000_profiles.sql on a throwaway project first, then apply it in the SQL editor or with supabase db push. Open Advisors, Security Advisor, and expect no warning on public.profiles. Then set these Auth options:

    • Confirm email on, and Confirm phone on.
    • Custom SMTP, so confirmation email reaches strangers.
    • Password minimum length 12.
    • Anonymous sign-ins off, and authenticator-app MFA on.
    • Site URL and Redirect URLs set to your production /console address only, with no wildcards.
    • Email templates for Confirm signup and Reset password that link to a query string (?token_hash=...&type=...), never a # fragment. The exact text is in README.md step 1.
    • JWT expiry 600 seconds, and asymmetric signing keys.

    Leaked-password protection needs a paid Supabase plan, so it is not on the Free plan. The full table is in README.md and docs/04-agent-console.md section 4.5.

  6. Turn on Google sign-in

    In Google Cloud, create an OAuth client of type Web application. Use the callback address that Supabase shows on its Google provider page as the authorized redirect URI. Turn on the Google provider in Supabase with the client ID and secret. The Google client secret lives only in Supabase.

  7. Create the GitHub token and protect main

    Create a fine-grained personal access token for this repository only, with Contents read and write and nothing else. No Workflows permission. Set it to expire in 90 days and rotate it then. Add a ruleset on main that blocks force pushes and deletions.

  8. Create the Anthropic key

    Create a dedicated workspace with a low spend limit, and an API key inside it. After the first chat, check that the spend shows in Anthropic's console.

  9. Put your Supabase host in the headers file

    public/_headers ships with https://<project-ref>.supabase.co in its content security policy. A headers file cannot read variables, so replace <project-ref> with your real host by hand. The build fails on purpose, at 0 credits, unless this host equals SUPABASE_URL. Never use a wildcard.

  10. Connect the repository to Netlify and set the variables

    Do this once you have a Netlify account. Add the site from the GitHub repository. Netlify reads netlify.toml (publish public, Node 22). Set the variables, and never set the Supabase secret or service_role key:

    netlify env:set ANTHROPIC_API_KEY <your-key> --context production --secret
netlify env:set GITHUB_TOKEN <your-token> --context production --secret
netlify env:set GITHUB_REPO fenago/BeachDay
netlify env:set SUPABASE_URL https://<your-project-ref>.supabase.co
netlify env:set SUPABASE_PUBLISHABLE_KEY <your-publishable-key>
netlify env:list --context production

    The two Supabase values and GITHUB_REPO are not secret and apply to all contexts, so do not mark the Supabase ones secret. Do not create GITHUB_READ_TOKEN unless Dr. Lee accepts ADR-0009. After you change a secret, deploy again so functions see it.

  11. Turn deploy previews off

    In Site settings, open Build and deploy, then turn off Deploy Previews and branch deploys. This is required, because only production should be able to read the secrets. Then run netlify env:list --context deploy-preview and check that the two secrets are absent. Keep Build without sensitive variables on for builds from forks. If you cannot turn previews off on the Free plan, tell the team, because the production check in the code is then the only barrier left.

  12. First deploy and smoke check

    Push to main. Each production deploy costs 15 of the 300 monthly credits on the Free plan, so batch your changes. A failed build costs 0, and a build skipped by the ignore rule should cost 0 (check the Usage page after the first skip). The Approve cap holds approvals to at most 210 credits, which is 70%. Watch for warnings at 70% (210) and 90% (270). Then check the site:

    BASE_URL=https://<your-site> EXPECT_COMMIT=<full-commit-sha> node scripts/smoke.mjs

  13. Make yourself super_admin

    On the live site, open Agents, create an account and confirm your email. Sign in the way you plan to sign in every day. Supabase's documentation says accounts with the same email are linked into one user automatically, but confirm that on your project before you run step 2. In the Supabase SQL editor, run step 1 of supabase/manual/promote-super-admin.sql with your address and read every check. Then run step 2 with the user id from step 1. Expect 1 row affected.

  14. Run the pre-launch tests (a) to (i)

    Run tests (a) to (i) on the real Supabase project and record the results. Approve needs (a) to (e), (g) and (i) to pass. Test (f) decides whether to switch the token-header pre-check on, and (h) checks that Netlify secret scanning does not flag the publishable key in config.js. If it does, set SECRETS_SCAN_OMIT_KEYS to SUPABASE_URL,SUPABASE_PUBLISHABLE_KEY as the fallback, and never turn scanning off. They cover sign-in timestamps, sign-out, the authenticator code, token headers, a Supabase outage answering 503, secret scanning and the profiles security check. The list is in docs/04-agent-console.md section 4.2 and in README.md.

  15. Turn Approve on

    Once tests (a) to (e), (g) and (i) pass, change approveEnabled to true in netlify/functions/lib/settings.mts. Get a security review, then push. That deploy costs 15 credits.

  16. Roll back if needed

    In Netlify, open Deploys, open the last good deploy, choose Publish deploy, then choose Lock to stop auto publishing. This costs 0 credits. Fix forward with git revert, then unlock. The full steps are in docs/runbooks/rollback.md.

  17. Add the test workflow by hand

    Agents cannot add a GitHub Actions workflow, so a person does it. Copy the template from knowledge/qa-engineer/examples/06-github-actions-no-secrets/ to .github/workflows/tests.yml, replace every placeholder with the full commit SHA of the action release, and keep it free of secrets. The steps are in README.md.

Every link used along the way is on the Resources page.
